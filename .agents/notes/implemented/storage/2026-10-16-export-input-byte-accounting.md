# 导出输入按原始 JSON 字节精确计数

日期：2026-10-16。状态：implemented。范围：Web 导出队列准入计数。

## 背景

真实批次启动采样出现长任务，调用栈包含整份输入的 JSON 序列化及 UTF-8 编码。图片正文占大部分字节，仅为容量判断而额外构造完整 JSON 和字节数组，扩大启动阻塞与瞬时分配。此处不改[后台导出决策](2026-10-14-background-pdf-exports.md)的接受、冻结与恢复语义。

## 决定

[计数函数](../../../../apps/mobile/src/local/export-input-bytes.ts)沿用 JSON.stringify 的对象遍历与转换；较长且没有转义字符、非 ASCII 码元的字符串值以空串参与序列化，并逐次累计原长度。只编码剩余 JSON，再加回省略正文的字节数。重复引用重复计数；引号仍由空串保留，数字、键、Unicode、转义、toJSON、未定义值及异常继续走标准行为。

[任务管理](../../../../apps/mobile/src/local/web-export-tasks.ts)仍按相同字节数执行原容量门槛，再 structuredClone 固定整个输入；不省略真实题图，不更改存储、队列或成品限制。

## 放弃的方案

直接按字符数计数会低估 Unicode，按固定倍率又会提前阻断原可接受内容，均未采用。整段 UTF-8 编码已有回归证明会分配整个图片正文。未添加工作线程或依赖：当前局部计数路径可保留同步准入及原冻结时点。图片正则替换另经微基准未显示有效正文收益，且自定义校验会影响错误或 schema 元数据，本次保留原验证。

## 后果与限制

不是流式生成器，也未消除快照重复验证、structuredClone、DOM 或 JPEG 绘制阻塞。大段 Unicode 或含转义的文本仍采用完整编码；优化条件只是内部阈值，不是新的输入容量限制。

## 验证

[回归](../../../../apps/mobile/src/local/export-input-bytes.test.ts)覆盖编码缓冲、边界、重复引用、不可变输入、Unicode/转义、标准转换与原容量判断；原实现因整段图片编码而失败，新实现通过。实际交互、取消和成品复测见[验收](../../../../docs/postmortem/2026-10-16-pdf-interaction-budget.md)。

## 2026-10-17 补充

同窗采样确认准入仍重复扫描长 ASCII 串。计数函数现仅在一次调用中保留至多64个已证明无转义的长 ASCII 值；同值免扫描，但每次仍全额计费。缓存不跨调用，不替代快照或图片校验，超出缓存沿原路径处理，计数/克隆保持同段。

单值复用在真实输入未改善，未采用；有界集合在相同输入微测有效。集合也有哈希开销，首轮独立串微测出现回退，不承诺任意输入提速。完整 JSON 计数、异常和容量判定不变，新增跨调用、缓存溢出及相近 Unicode/转义回归。实测边界和当前构建复核见[准入扫描验收](../../../../docs/postmortem/2026-10-17-pdf-admission-scan.md)。
