# 简洁解题的首响应与停滞保护

日期：2026-11-09。状态：implemented。范围：共享设备解题与采用同一解题器的中心考试工作进程。

## 背景

固定阶段窗口能限制总等待，但不能区分仍在生成和已经没有进展。2026-11-09 对中心考试历史数据的只读分析中，慢题前三例均在主调用约240 秒失败后才接手；1031 次成功主调用最长79.894 秒。样本支持保守的首响应保护，不能证明未来所有题或供应商都适用。

## 决定

[契约](../../../../packages/contracts/src/agent.ts)拥有90 秒首内容、60 秒输出停滞窗口。[请求进展](../../../../packages/agent/src/pi/request-progress.ts)按真实网络派发启动，非流式同样适用；[设备阶段](../../../../packages/agent/src/pi/mobile.ts)只对有既有接手机会的简洁主解题启用。隐藏推理沿原60 秒规则，连续有正文的请求保留原阶段预算；工具执行与名额排队不触发请求停滞。

超时终止当前阶段，直接消耗既有一次接手机会，不增加原模型重试、接手次数或目的地。用户取消优先，已清除的定时回调及旧派发通知用代次隔离；退出、工具轮次和新请求都释放旧定时器。可信传输可延迟通知实际派发，协议头和模型输入不参与控制。

诊断把响应头和首个内容事件分开，错误仅使用固定分类；不记录题目、正文或隐藏推理。当前行为由[传输文档](../../../../docs/subsystems/model-transport.md)维护。

## 放弃的方案

- 统一缩短阶段预算：会切断持续正常输出及工具处理。
- 把HTTP响应头或SSE保活当作进展：服务商仍可长期不返回内容。
- 在等待并发名额时计首响应：会把本地排队误判为模型停滞。

## 后果与限制

供应商极慢但最终可成功的请求可能被提前接手；本次未做真实付费准确率或耗时对比。没有接手模型、详细学习、备用及核验保留原阶段行为。首内容包含SDK上报的推理增量，不能等同首个可见答案。

本地UI另把秒表显示改为每秒且仅前台更新，回前台按持久化墙钟补齐，实际作答时间不暂停；相同块公式复用渲染，提示关闭目标统一44逻辑像素。不增加独立动画系统。

## 验证

回归覆盖静默、保活、部分内容停滞、持续进展、取消竞争、工具间隙及排队派发，详见[双分支验收](../../../../docs/postmortem/2026-11-09-shared-progress-ui.md)。浏览器视口不代表iOS或Android真机验收。
