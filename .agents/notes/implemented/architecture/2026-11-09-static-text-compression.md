# 公开静态文本的流式压缩

日期：2026-11-09。状态：implemented。范围：完整Web客户端的Node静态服务与Docker发布，不含中心考试独立服务。

## 背景

Mac升级验收中，跨网络加载首页成功，但主JS在45秒内未完成；一次冷启动页面显示默认8路，服务器仍为32路；配置读取受慢链路影响是推测。此前静态服务直接传输约3.2MB主脚本，没有Content-Encoding。Mac本机两个HTTPS入口及配置摘要正常，不能把网络下载慢归为模型生成耗时。

## 决定

[静态服务](../../../../scripts/web-server.mjs)对至少1KiB的公开HTML、JS、CSS、SVG与文本按Accept-Encoding选择Brotli/gzip；尊重q=0和编码质量，包含Vary，不对压缩响应声明原始Content-Length。小文件与图片不压缩，私有环境、模型代理、API与SSE在这一路径之前返回。

使用Node内置压缩流与pipeline，无新增依赖；Brotli质量4、窗口20，gzip级别6，文件和编码流随取消/错误一起销毁。HEAD只返回所选编码的头部，既有不可变codec缓存保持。当前部署规则见[Docker指南](../../../../docs/cookbook/docker-web.md)。

## 放弃的方案

- 仅延长浏览器验收或环境读取超时：不能减少下载量，容易掩盖慢链路失败。
- 先增加构建预压缩副本：会扩大发布文件与摘要格式；现有小规模私有实例优先使用内置流，不引入缓存淘汰机制。

## 后果与限制

每次公开文本请求增加压缩CPU开销，内存受流缓冲和压缩窗口约束；不声称持续并发容量已有压测。压缩不改变解题、上传预算或模型请求内容，不能保证所有网络路径都达到固定首屏时限。
