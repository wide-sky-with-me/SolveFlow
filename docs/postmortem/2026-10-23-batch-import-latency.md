# 手机照片批量确认后的等待与卡顿分析

日期：2026-10-23。范围：用户反馈50张手机照片确认顺序后等待题目列表/开始答题。仅分析现有Web路径，应用源码、远程部署和真实题库均未修改，优化尚未实施。

## 测试条件

i7-12800HX、WSL2 Linux、Chrome154.0.8037.97、Node24.19.0。本轮独立回环服务加载当前已构建Web，入口版本与3131一致；临时浏览器及合成IndexedDB隔离，不借用用户存储。

50个不同文件名使用同一张合成手机照片：4032×3024、JPEG6294997字节，输入合计约300MiB。预置250条合成历史，目标批次仅1张，其余为单题。确认窗口显示50行后点击，计时至窗口关闭；选图阶段另记。解题并发16，模型请求全部拦截并挂起，测量后中止；不等待真实答题或付费。每条件仅一次观测，不构成设备性能承诺。

证据为权限700的`.runtime/batch-import-profile-2026-10-23/`，含脚本、合成图片、逐阶段统计与CPU采样。首次夹具未完成文件选择，在关闭后报filechooser等待失败，`profile.log`保留且不纳入计时；修正定位范围与文件名位数后重跑。

## 原因

1. [导入循环](../../apps/mobile/src/components/batch-import.tsx)逐张等待`onAdd`，每张完成后才处理下一张，全部结束才关闭顺序窗口。[保存入口](../../apps/mobile/src/components/batch-capture.tsx)又逐张执行图片变换、Base64读取、建记录及入队。已有部分题目进入后台队列时，预览仍覆盖题目列表。
2. 手机大图会再次发起解码，缩放至2048并编码JPEG后读取Base64。普通新建样本50次bitmap调用累计约9.64秒，JPEG约3.17秒、Base64约1.23秒；这些调用是逐张链路的一部分。归一化JPEG总量约71MiB，原图输入约300MiB。尺寸预览也需解码，图片列表直接引用原图URI；未测浏览器解码缓存或GPU内存峰值。
3. [已有批次追加](../../apps/mobile/src/components/batch-workspace.tsx)未传已知位置，保存入口每张调用未缓存的`listHistory()`来计算下一序号。[仓库](../../packages/client/src/local-repository.ts)在`getMany`缺失时逐条读取摘要及收藏，当前[Web适配](../../apps/mobile/src/local/documents.web.ts)没有该接口，每次读取独立事务。250至299条历史累计正好13725次摘要、13725次收藏读取；50次完整扫描耗约17.79秒，CPU压力下约98.53秒。仓库串行锁还令其他保存与刷新排队。
4. 追加路径逐张切换当前题并显式刷新，保存通知同时触发订阅刷新；普通追加测得298次缓存历史调用、116次完整记录读取。顺序窗口每导入一张就移除首行，剩余行的序号、按钮和布局重算。新建普通样本有48次超过50毫秒的任务，累计约5.33秒、最长237毫秒；CPU压力追加样本最长任务1.20秒、帧间隔1.48秒，等待期间还会短暂不跟手。

方法调用和事务计时含异步重叠及锁等待，不能直接把各项总和相加当作耗时占比。图像处理、存储和请求准备均在浏览器端发生，增加服务端模型并发不会消除这些步骤。

## 优化顺序与边界

已有批次优先复用已确认的位置计数，避免逐图扫描全部历史；补齐Web有界批量读取。所有路径再处理图像流水线：有限并发、减少重复解码与大字符串复制，并限制主线程重活。导入进度与底层题目列表分批刷新，减少逐张切题和全行重排；保留顺序、先保存后入队、停止/退出及失败后仅重试剩余图片的语义。

尚未实现上述优化，未在用户实际照片或电脑上录制一至两分钟的耗时，也未验证Android/iOS。合成图片内容重复、预览立即确认、无真实模型完成事件及诊断插桩都会影响绝对数值；结论限定为现有流程的可复现开销。

复现实验命令为`node .runtime/batch-import-profile-2026-10-23/profile.mjs`；压力对照追加`ONLY_CASE=capture`或`append`、`CPU_SLOWDOWN=4`及独立`RUN_LABEL`。执行环境需可启动Chrome，准确服务URL/PID由本轮`test-server.json`记录。验收后关闭全部浏览器和本轮服务，保留合成样本及采样；文档检查结果见`docs-final.log`。没有运行应用构建或单元回归，也不将性能观测称为实现修复。
